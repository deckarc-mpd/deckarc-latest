Architecture Freeze
This document supersedes prior v2/v3 architectural interpretations. The business domains are enterprise-scale; the implementation remains deliberately lean. CP360 must not over-agentize, over-service, or over-infrastructure the platform.
 
1. Executive Decision
CP360 will be built as an AI-native construction operating system, not as a collection of chatbots. The platform must support enterprise-scale operations while remaining inexpensive and simple to run at DeckArc's current scale.
Core Rule
Design boundaries for a multi-billion-dollar business. Build infrastructure for today's measured load. Scale components only when real usage, reliability or organizational load proves the need.
•	The AI workforce is native to CP360. No standalone DeckArc AI application.
•	The user experience is one calm operating product: Command Center, Action Center, Projects, and Voice.
•	The initial workforce is limited to six meaningful agents.
•	Finance is initially deterministic services + SOP workflows, not a separate AI executive.
•	Audit is P1 foundation infrastructure, not a later reporting feature.
•	Scheduled operations are first-class triggers using the same workflow system as UI, voice and integrations.
•	Gmail, Google Calendar and Google Drive use one shared Integration Gateway.
•	One governed Knowledge Brain. No vector database or memory store per agent.
•	The Chief of Staff is an executive intelligence/compression agent, not the technical router.

3. What Is an Agent vs. a Service?
Do not equate an org-chart box with an AI agent. Use this test before creating any new agent.
Question	If YES	If NO
Does it own an ongoing business outcome?	Agent candidate	Prefer service/SOP
Does it require interpretation across changing context?	Agent candidate	Prefer deterministic code
Does it make bounded decisions within authority?	Agent candidate	Prefer workflow/rules
Does it manage multi-step work over time?	Agent candidate	Could still be workflow
Does it handle meaningful exceptions?	Agent candidate	Prefer normal automation
Would a separate identity materially improve ownership, permissions or evaluation?	Agent candidate	Keep under existing agent
Agent Creation Gate
Every proposed new agent must document why an SOP, deterministic service, workflow, or capability under an existing agent is insufficient. If that case is weak, do not create the agent.

14. Explicit Cost-Control Rules for Claude Code
Non-Negotiable
Claude Code must not introduce enterprise infrastructure merely because the future architecture could use it. Create clean replaceable boundaries first. Physically split or scale components only after measured need.
Claude Code must NOT introduce the following unless one of the approval conditions below is met:
Do NOT introduce by default	Approval condition
Kubernetes	Existing CP360 already relies on it OR measured deployment/load/reliability requirement cannot be met simply
Dozens of microservices	A module has independently measured scaling/reliability/deployment needs that justify extraction
Separate runtime per agent	Isolation/scaling/security evidence proves a shared runtime is insufficient
Vector database per agent	Never by default; one governed knowledge layer unless a proven hard isolation requirement exists
Event infrastructure per department	Never; use one event abstraction/fabric
Multiple queues because 'enterprise'	Only if workload classes require independent durability/priority/scaling
Giant data warehouse	Only when operational/reporting needs exceed transactional/reporting patterns and ROI is documented
Elaborate agent-to-agent chat	Avoid; use structured events/workflows/canonical state
Separate voice business logic	Never; voice must invoke the same SOPs/tools/policies
LLM for deterministic calculations	Never unless the output is explanatory, not authoritative math
Duplicate connector per agent	Never; use Integration Gateway
Duplicate knowledge store per agent	Never; use scoped shared Knowledge Brain
•	Prefer a modular monolith using the existing CP360 deployment unless Phase 0 proves a stronger reason.
•	Logical modules may be independently extractable later without being separately deployed today.
•	Every new infrastructure component requires a short ADR documenting problem, cheaper alternatives considered, measured evidence, expected cost, and rollback.
•	Every AI invocation must answer: Why can deterministic code not do this reliably?
•	Every new agent must answer: Why can an SOP/service under an existing agent not own this?
•	Every recurring scheduled job must answer: Can a deterministic change detector avoid the AI call?
•	Every new data store must answer: Why can the canonical CP360 DB / existing storage not safely serve this need?

23.6 AI Invocation Gate

2.	What deterministic pre-filter reduces input to only relevant exceptions?
3.	What structured output schema will be enforced?
4.	What authoritative data source is used?
5.	What happens if the model is unavailable or malformed?
6.	What is the cheaper model class that can reliably perform this task?
7.	How will AI cost be measured by agent/SOP/workflow/company?
