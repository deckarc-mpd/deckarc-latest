# CP360 Scheduled Operating Events

Defines the scheduled operating rhythm required by Frozen Architecture v4 §11 and §20, mapped against what currently exists (nothing — see `CP360_AI_PHASE0_DISCOVERY.md` §6) and how it should be built per `ADR-CP360-AI-002_LEAN_INFRASTRUCTURE.md`'s lean-infrastructure decision. This document defines *what* runs and *when*, and the mechanism; it does not implement anything (Phase 0 is documentation-only).

---

## 1. Current State (baseline)

Zero scheduled execution exists. Every "check" in the product today (alert colors, Action Board categorization, delay cascades) is computed synchronously, in the browser, only while triggered by a user action or an open page (Phase 0 Discovery §6). There is no cron, no queue, no scheduled function, and no persisted "last checked at" state for any sweep. This document assumes a Phase 1/4 build starting from that empty baseline.

## 2. Mechanism Decision

Per `ADR-CP360-AI-002`, scheduling uses **the platform's existing job mechanism first**:

- **Primary mechanism**: Vercel Cron Jobs (configured in `vercel.json`'s `crons` key, currently absent) invoking Vercel Serverless Functions that run deterministic sweep logic against Supabase, exactly like the existing `api/*` functions already do for the Gemini proxies.
- **Alternative/complement**: Supabase's own scheduled-jobs capability (`pg_cron` extension) for sweeps that are pure SQL/deterministic and don't need to call out to an LLM or external API — cheaper and simpler than round-tripping through a Vercel function when the whole sweep is "update a status column based on a date comparison."
- **Not used in this phase**: any dedicated workflow-orchestration product (Temporal, Airflow, Step Functions) or message broker — no measured throughput evidence justifies them yet (frozen §25).
- **Minimum interval / granularity**: cadences below are expressed at the granularity the frozen architecture specifies (e.g., "Morning," "Midday"); the underlying cron mechanism should run frequently enough to hit each named cadence within its company-configured window, not necessarily every minute — most sweeps are daily or a few times a day, so cost and load stay minimal by construction.

## 3. Non-Negotiable Rule (frozen §11, restated for implementers)

**Every scheduled entry point runs a deterministic check first. It calls AI only if the deterministic check finds a material exception, and it makes zero AI calls if nothing changed.** This is not a performance optimization to consider later — it is the acceptance criterion for every sweep listed below. A sweep implementation that always calls an LLM "to be safe" fails this requirement regardless of how well it works.

## 4. Company Configurability Requirements

Every cadence below must be configurable per company (per `organizations`), not hardcoded:
- **Timezone** — not yet a column on `organizations`; must be added (Gap: no timezone field exists on any table today).
- **Business calendar / holidays** — `project_calendars` (working-day flags per project) and `us_holidays` (seeded federal holidays) already exist and are already consumed by `scheduleEngine.ts`'s date math; scheduled sweeps should reuse these tables rather than duplicating holiday logic, and should be extended to a **company-level** default (today `project_calendars` is per-project only — there's no company-wide default row a new project inherits from, which is a small but real gap to close in Phase 1/4).
- **Project-status exclusions** — sweeps must skip projects in terminal/paused states (`Completed`, `Cancelled`/`Archived`, `On Hold` where applicable) using the existing `projects.status` field; no new schema needed here, just correct sweep logic.

## 5. Deduplication Requirement

Every scheduled sweep must check whether a material exception it would raise already has an open, unresolved audit/action-item record before creating a duplicate, and must not re-trigger a workflow that an event-driven trigger (e.g., a user action, or a future Integration Gateway event) already started for the same underlying fact. This depends on the audit/correlation infrastructure being built in Phase 1 (see `CP360_AI_GAP_ANALYSIS.md` §1) — scheduled sweeps should not ship before that exists, or duplicate-action rate (a named Frozen §13 cost-governance metric) will be impossible to keep near zero.

## 6. Operating Clock

Times below are **default configuration examples**, matching frozen §20 Figure 13, expressed relative to each company's configured timezone/business calendar. Every row states the deterministic-first check and the AI escalation condition explicitly, and the CP360 data/module it reads (so implementers know exactly what exists to build on, per Phase 0 Discovery).

| 06:30 | Project readiness calculations | Project Ops (`project_operations`) | Recompute `calculateTaskAlert`/`calculatePermitAlert`/`calculateInspectionAlert`/`calculateDecisionAlert`-equivalent logic (today client-render-time only, per Phase 0 Discovery §6) as a persisted sweep over `tasks`, `permits`, `inspections`, `client_decisions` for active projects (`projects.status` not terminal). | AI only if a task/permit/inspection newly crosses into `red` (blocking) status with no existing open action item. | Reads: `tasks`, `permits`, `inspections`, `client_decisions`, `project_calendars`, `us_holidays`. Writes: exception/action-item records (extends `action_items`). |
| 07:00 | Trade / material / inspection rule checks | Project Ops / Compliance (`compliance`) | Check `materials.expected_delivery_date` vs. today, `ProjectInspectionRequirement` sequencing/prerequisites, `crew_confirmations.confirmation_status` for tomorrow's scheduled work. | AI only for exceptions needing interpretation (e.g., a material delay whose cascading schedule impact isn't a simple date push — hand to `cascadeDelayFromTask` deterministically first; AI only drafts the human-facing explanation if requested). | Reads: `materials`, `project_inspection_requirements` (table name per migration: `ProjectInspectionRequirement`), `crew_confirmations`. Draft requires admin approval before send (frozen §5 Finance-style ambiguous-only AI pattern, applied here to comms). | Reads: `communication_log`, `client_decisions`, `tasks.client_visible_notes`. Writes: draft record for admin approval (new; distinct from the existing non-AI `AiSummaryTab`'s "Client Update" template generator, which this should eventually supersede — see Gap Analysis §5). |
| 17:00 | Tomorrow plan finalization | Project Ops | Roll up 15:00/16:00 results into a finalized "tomorrow" record for Field Mode / Tomorrow's Plan page (`TomorrowWorkPage.tsx` already exists as the UI target). | None — synthesis already happened at 15:00; this is deterministic rollup. | Writes: tomorrow-plan record consumed by `TomorrowWorkPage.tsx`. |
| 17:30 | End-of-day close / tomorrow setup | Chief of Staff | Deterministic scan: any items still open from the day's sweeps that are unresolved by end of day. | AI synthesizes only the unresolved material items into an end-of-day note — mirrors the 07:30 pattern. | Reads: day's action-item/exception records. |

| Weekly | Executive Portfolio Review | Chief of Staff | Deterministic aggregation of the week's KPI/exception counts (reuses the same exception records as the daily sweeps, aggregated). | AI synthesizes the weekly narrative only from the aggregated counts, not by re-reading raw project data. | Reads: week's exception/action-item records. |
| Monthly | Knowledge Review | System + human reviewers | Deterministic diff of what changed in the (future) Knowledge Brain's source tables since last review. | AI proposes candidate knowledge updates (frozen §10: "AI proposes; governed promotion") — a human always promotes, per the frozen governance model; no auto-publish. | Reads/writes: Knowledge Brain tables (not yet built — Phase 1+). |

## 7. Audit Requirement (frozen §23.8)

Every scheduled run — whether it found zero exceptions or many — must record a run entry (workflow_id/SOP version, trigger = "schedule", start/end time, exceptions found, AI calls made, actions taken) in the audit system defined in Phase 1 (per `CP360_AI_GAP_ANALYSIS.md` §1/§7). A sweep that silently runs with no audit trail is not acceptable even if it made zero AI calls and took zero actions — "nothing happened" is itself a fact worth recording for reliability monitoring (the "Workflow success rate" and "Duplicate action rate" metrics in frozen §13 depend on this).

## 8. What This Document Deliberately Does Not Do

This is a specification of cadence, ownership, and the deterministic-first/AI-escalation contract per routine — it is not:
- A cron expression list (exact trigger times are a Phase 1/4 implementation detail, configurable per company per §4 above).
- A workflow engine design (see the not-yet-written Phase 1 SOP/workflow architecture — out of scope for Phase 0 per the user's explicit instruction to stop after documentation).
- A schema migration (no tables are created by this document; every "Reads/writes" cell above references either an existing table found in Phase 0 Discovery or flags a new one needed, for the Implementation Plan to schedule).
