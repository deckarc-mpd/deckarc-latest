# CP360 AI Cost Baseline

**Phase:** P0 deliverable.
**References:** `docs/ai-brain/brain.txt` §13 ("AI Control Plane & Cost Governance"), §23.3 ("Cost Baseline Required Before New Infrastructure"); `CP360_AI_PHASE0_DISCOVERY.md`.

## 0. Important Caveat

**No billing dashboards, usage logs, or cost-tracking code exist anywhere in this repository.** Nothing in the codebase records request volume, token usage, or spend. The figures below are therefore **stated assumptions**, clearly labeled as such, not measured data — exactly the situation brain.txt §23.3 anticipates when it requires documenting "current stack and cost-impact assumptions" before proposing new infrastructure. Section 4 lists what would need to be instrumented to replace these assumptions with real numbers; that instrumentation is itself a P1 deliverable (model routing + cost logging, per `CP360_AI_IMPLEMENTATION_PLAN.md` P1 item 9).

This baseline is close to a blank slate — there is no existing AI cost to protect or migrate away from, which simplifies P1's cost-governance design but means every number in Section 2 below is a genuinely new cost, not a delta from something already being paid for.

## 2. Cost-Impact Template for New P1+ Components

Per brain.txt §23.3, every proposed new component must document: problem solved, why existing capability is insufficient, simpler alternatives considered, current measured load/failure mode proving need, expected monthly fixed/variable cost, operational burden, exit/rollback plan, and the future metric that would trigger scaling. Applied to each P1 foundation component (all judged against ADR-CP360-AI-002's lean-infrastructure default — i.e., none of these introduce new infrastructure categories, only new tables/functions inside the existing Supabase/Vercel surface):

| Component | Problem it solves | Why existing capability is insufficient | Simpler alternative considered | Expected monthly cost | Operational burden | Trigger to scale further |
|---|---|---|---|---|---|---|
| Extended audit tables (§P1.1) | No correlated, typed audit trail exists (`activity_log` is flat) | `activity_log` lacks correlation/workflow/company columns and record-type discrimination required before autonomous writes are safe | Add columns to `activity_log` in place rather than new sibling tables — chosen where it doesn't compromise query clarity | Marginal — same Postgres instance, additional storage only (rows are small; no new service) | Low — standard migration + index maintenance | Audit table growth harming OLTP/reporting performance (brain.txt §25) → dedicated audit/event store |
| Event abstraction table + dispatcher | No shared event model across UI/scheduler/voice/integrations | Nothing exists; every action is a direct DB call today | A message broker (SQS/PubSub) — rejected, no measured throughput need (ADR-002) | Marginal — same Postgres instance + existing serverless function execution time | Low | Workflow throughput exceeds existing job mechanism (brain.txt §25) → dedicated durable workflow/event infrastructure |
| Agent/SOP registry tables | No agent concept exists | N/A — greenfield, six rows seeded per employeeidentity.txt | A config file instead of a DB table — rejected, brain.txt wants configurability without redeploys | Marginal — a handful of small tables | Low | N/A at this scale (6 agents, one company) |
| Controlled Tools layer (new Edge/serverless functions) | No server-side tool-execution surface; all writes are direct client-to-Supabase | Client-executed tools (current `api/voice-assistant.ts` pattern) can't be policy-gated or audited centrally | Keep tool logic in frontend — rejected, violates brain.txt's controlled-tools/audit requirements outright | Vercel/Supabase function invocation cost — likely still within free/low-tier allowance at pilot scale; **real cost only known once instrumented (Section 4)** | Medium — new deploy surface to test/monitor, though still inside existing platforms | Tool/connector failure rate or invocation volume crossing the hosting tier's included quota |
| Policy/Authority engine + Approvals tables | No formal authority/consequential-action gating exists | Current gating is a hardcoded email check and an informal `WRITE_TOOLS` set in one file | A hardcoded per-feature `if` check per action — rejected, doesn't scale past a handful of actions and can't be audited/configured centrally | Marginal — same Postgres instance | Low–Medium — policy rules need review as new SOPs are added | N/A at this scale; revisit if policy rule count grows large enough to need a dedicated rules engine |
| Feature flags table | No way to gate AI rollout incrementally | Nothing exists; today's "rollout control" is literally a hardcoded email string | LaunchDarkly/similar SaaS flag service — rejected as unnecessary infrastructure for current scale (ADR-002) | Marginal — one small table | Low | N/A at this scale |
| Model routing + cost-logging module | No cost visibility into any AI call (this document's core caveat) | Both existing Gemini calls hardcode the model name with zero logging | Rely on Vercel/Google's own dashboards only — rejected, doesn't give per-agent/per-SOP/per-company attribution required by brain.txt §13 | Marginal engineering cost; the module itself has no direct spend, but it's the prerequisite for knowing what real model calls will cost once Claude/Anthropic (or any provider) is wired in for the six agents | Low | N/A — this *is* the instrumentation that removes future guesswork |
| Scheduler (`pg_cron` or Vercel Cron) | No scheduled/background execution exists | Nothing to extend | A third-party scheduling SaaS — rejected, `pg_cron` is already available inside the existing Supabase Postgres instance (ADR-002) | Marginal — `pg_cron` has no separate billing line on Supabase; Vercel Cron has a small included allowance on paid tiers | Low | Workflow/scheduling complexity exceeding what cron-style triggers can express (brain.txt §25) |
| Integration Gateway (Gmail/Calendar/Drive OAuth + connector) | No real integration exists at all | N/A — greenfield build | Per-agent connectors — explicitly rejected by brain.txt §14's Do-Not-Build list | Google Workspace API usage is typically free at CP360's likely call volume (Gmail/Calendar/Drive APIs have generous free quotas); **real cost only known once connected and instrumented** | Medium — OAuth flow, token refresh, and connector health monitoring are genuinely new operational surface, even though hosted inside the existing backend | Connector volume causing independent scaling/failure needs (brain.txt §25) → dedicated connector workers |
| Real AI provider calls for the six agents (Claude/Anthropic or continued Gemini) | Six named AI employees (employeeidentity.txt) need real reasoning capability, not the current deterministic mock (`AskCP360.tsx`) or single-user Gemini prototype | `AskCP360.tsx` does no real inference at all; the two Gemini functions are single-user prototypes with no cost governance | Stay on Gemini free tier indefinitely — rejected as a long-term plan once usage moves beyond a single admin account and real reasoning/tool-use volume grows across six agents and multiple users | **Unknown — the single most important number this baseline cannot state without a provider/model decision and measured call volume.** Must be estimated per-agent once P1's model-routing module can log real token/request counts against a pilot workload | Medium-High relative to everything else in this table — this is the first component with a plausible non-trivial recurring bill | AI cost per SOP/workflow or per company crossing an approved budget threshold (brain.txt §13's own named metric) |

## 3. What This Baseline Deliberately Does Not Claim

- It does not state a total monthly AI budget figure, because no real agent has run yet and no provider/model decision has been finalized in this document (that's a product-owner decision, not a Phase 0 discovery finding).
- It does not assume Claude/Anthropic pricing, since model selection is out of scope for Phase 0 inspection and is explicitly flagged as an open question in `CP360_AI_PHASE0_DISCOVERY.md` §14.
- It does not claim Vercel/Supabase tier names or dollar figures, since no billing configuration is visible in the repository — stating a specific number here would misrepresent an assumption as a fact.

## 4. Instrumentation Needed to Replace Assumptions With Real Numbers

1. Vercel and Supabase plan/tier confirmation (product-owner-provided, not discoverable from the repo).
2. The model-routing + cost-logging module (P1 item 9 in `CP360_AI_IMPLEMENTATION_PLAN.md`) — once live, every AI call logs tokens/cost/latency against `agent_id`/`workflow_id`/`company_id`, which directly produces the brain.txt §13 metrics ("AI cost per SOP/workflow," "Cost per company/project," "Model/provider usage").
3. Integration Gateway call-volume logging once Gmail/Calendar/Drive connectors exist, to confirm they stay within Google's free API quotas at CP360's actual usage level.
4. A lightweight monthly rollup (even a manual one initially) comparing actual Vercel/Supabase/model spend against this baseline's assumptions, so cost governance is a running practice from P1 onward rather than a one-time Phase 0 exercise.
